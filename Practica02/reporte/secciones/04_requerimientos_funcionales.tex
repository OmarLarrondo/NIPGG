\section{Requerimientos funcionales}

Los requerimientos funcionales describen el comportamiento observable del
prototipo y permiten vincular las necesidades de PuellaGame con las operaciones
que ofrece la aplicación. Cada requerimiento se formula de manera verificable y
se aplica, cuando corresponde, a las entidades \emph{Sucursal}, \emph{Premio} y
\emph{Cliente}.

\begin{enumerate}[label=\textbf{RF-\arabic*.}, leftmargin=*]
    \item \textbf{Administrar entidades.} El sistema deberá permitir registrar,
    consultar, editar y eliminar sucursales, premios y clientes desde una
    interfaz de consola.
    \item \textbf{Registrar información.} Para cada alta, el sistema solicitará
    los atributos definidos para la entidad, validará la entrada y rechazará un
    identificador que ya se encuentre registrado.
    \item \textbf{Consultar por llave.} El operador proporcionará el
    identificador de una entidad y el sistema devolverá todos los datos del
    registro correspondiente o informará que este no existe.
    \item \textbf{Editar información.} El sistema conservará la llave del
    registro seleccionado y sustituirá sus demás atributos por valores nuevos
    previamente validados.
    \item \textbf{Eliminar información.} El sistema solicitará confirmación
    antes de retirar de forma persistente el registro identificado.
    \item \textbf{Persistir en CSV.} Cada cambio deberá guardarse de inmediato
    en el archivo asociado con la entidad: \texttt{sucursales.csv},
    \texttt{premios.csv} o \texttt{clientes.csv}. Al iniciar una ejecución, el
    sistema deberá leer los registros existentes.
    \item \textbf{Validar entradas.} Los identificadores deberán ser enteros
    positivos; los puntos y existencias, enteros no negativos; los textos
    obligatorios no podrán estar vacíos; los correos deberán tener un formato
    válido y los teléfonos deberán contener diez dígitos.
    \item \textbf{Manejar errores.} Ante datos inválidos, llaves ausentes o
    duplicadas y fallos de lectura o escritura, la aplicación deberá explicar
    la causa al operador sin finalizar inesperadamente y permitirle continuar.
    \item \textbf{Navegar por menús.} El menú principal deberá dar acceso a las
    tres entidades, y cada submenú deberá ofrecer las cuatro operaciones CRUD,
    además de una opción para regresar o salir.
\end{enumerate}

Las entidades comparten un identificador entero y único. \emph{Sucursal}
conserva nombre, dirección y teléfono; \emph{Premio}, nombre, descripción,
puntos requeridos y existencias; y \emph{Cliente}, nombre, correo, teléfono y
puntos acumulados. El operador autorizado es el actor que ejecuta las acciones,
mientras que el administrador recibe la información resultante para apoyar la
gestión del centro.
